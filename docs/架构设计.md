# 轻量应用服务器多服务架构设计

> 华为云轻量应用服务器（2核2G）· Docker Compose · 单机多服务 · 学习实验环境

---

## 1. 设计定位

本架构服务于一个**单机学习实验环境**：在一台 2核2G 的轻量服务器上持续运行多个自建服务，并保持低成本接入新服务的能力。

由此推导出的架构性质：

| 性质 | 决策 |
|---|---|
| 环境非生产 | 不设计备份、容灾、高可用、多机部署、生产级监控告警 |
| 内存为第一约束 | 所有组件强制声明资源上限，容量纳入架构管理（见 §7） |
| 服务可插拔 | 服务以目录为单位组织，接入/移除不触碰其他服务的配置（见 §4、§6） |
| 站点即服务 | 个人站需要 API 与动态页，按普通服务接入、走 SSR，不再假设"前端是纯静态"（见 §6.2） |
| 入口唯一 | 所有 HTTP 流量收敛到单一入口层，业务服务不直接对外 |
| 关注点分离 | 网络按前端/后端分域，数据库不可从外部到达（见 §3） |

---

## 2. 总体架构

```
              华为云安全组（边界：仅放行 22 / 80）
                        │
            ┌───────────▼─────────────────┐
            │   轻量应用服务器 2C2G         │
            │                              │
            │  [入口层] Nginx :80           │
            │        │ 按路径全部反代        │
            │   ┌────▼────────────────┐    │
            │   │  web-net            │    │
            │   │ ┌─────────────────┐ │    │
            │   │ │ site (Astro SSR)│ │    │
            │   │ │ 页面 + API       │ │    │
            │   │ └────────┬────────┘ │    │
            │   └──────────┼──────────┘    │
            │   ┌──────────▼─────────┐     │
            │   │  db-net            │     │
            │   │ ┌────┐ ┌────┐      │     │
            │   │ │PgSQL│ │Redis│     │     │
            │   │ └────┘ └────┘      │     │
            │   └────────────────────┘     │
            └──────────────────────────────┘
```

`site` 是个人站对应的容器：页面和 API 跑在同一个 Node 进程里。
`apps/` 若启用则是入口层容器里的只读文件，不进网络——但当前未使用（见 §5.2）。

| 层 | 组件 | 职责 | 对外暴露 |
|---|---|---|---|
| 边界层 | 华为云安全组 | 公网访问控制 | 22 / 80 |
| 入口层 | Nginx | 统一 HTTP 入口，按路径反代到服务 | 80 |
| 服务层 | 业务应用容器（含 `site`） | 页面、API 与业务逻辑；每服务独立目录、独立 compose | 无（仅经入口层） |
| 数据层 | PostgreSQL / Redis 等 | 持久化与中间件 | 无（仅 db-net） |

## 3. 网络设计

### 3.1 网络分域

| 网络 | 成员 | 作用 |
|---|---|---|
| `web-net` | Nginx + 全部业务服务 | 入口层到服务层的流量通道；容器名即内部 DNS |
| `db-net` | 需要数据的业务服务 + 数据组件 | 服务层到数据层的通道 |

隔离规则：

- Nginx **只**接入 `web-net`，数据组件**只**接入 `db-net`——入口层与数据层在网络层面互不可见。
- 业务服务按需接入两网：无数据依赖的服务不挂 `db-net`。
- 需要 API 或动态渲染的站点，按服务接入、挂在 `web-net` 上——个人站 `site` 就是这种情况。
- 纯静态站（`apps/`，当前未启用）不加入任何网络：它不是容器，只是入口层容器里的只读文件，
  因此天然到不了 `db-net`，也无需在网络上做额外隔离。
- 数据组件一律不声明 `ports:`，公网不可达由「安全组 + 无端口映射」双重保证。

### 3.2 边界端口

| 端口 | 用途 | 状态 |
|---|---|---|
| 22 | SSH | 常开 |
| 80 | 统一入口 | 常开 |
| 8000~8099 | 服务调试预留 | 默认关闭，调试时临时放行 |

## 4. 目录结构约定

```
<repo>/
├── compose.yml              # 总入口：include 全部子服务
├── nginx/
│   ├── compose.yml
│   └── conf.d/default.conf  # 路由定义：按路径反代
├── services/
│   ├── _template/           # 服务接入模板
│   │   ├── compose.yml
│   │   ├── .env.example
│   │   └── README.md
│   ├── site/                # 个人站：Astro SSR，页面 + API
│   │   ├── src/
│   │   ├── Dockerfile
│   │   └── compose.yml
│   └── <service-name>/      # 一个服务一个目录
├── apps/                    # 纯静态站（可选路径，当前未使用）
│   └── <app-name>/
├── data/<service-name>/     # 全部持久化数据的统一挂载根
├── scripts/                 # 网络初始化、服务脚手架
└── docs/                    # 设计文档：架构设计 / Docker速查
```

四条结构性规则：

1. **目录即服务**：每个服务目录内含完整自描述的 `compose.yml`，可独立部署，也可被总入口聚合——接入与移除互不牵连。
2. **数据归位**：持久化数据统一写入 `<repo>/data/<服务名>/`，服务销毁重建不丢数据。
3. **配置外置**：端口、名称等环境差异项一律写入 `.env`，不散落在 yml 中。
4. **有没有进程决定归属**：需要 API、鉴权或动态渲染的进 `services/`（个人站即如此）；
   只产出静态文件的才考虑 `apps/`。`apps/` 不占网络、不占容器内存，但也没有任何服务端能力，
   并且缺独立的重启策略与资源配额——这是它省内存的代价，不是免费的隔离。

## 5. 入口层设计

### 5.1 路由模型

当前无域名，入口采用 **IP + URL 路径** 分发；后续引入域名后可平滑切换为按子域名分发，目录结构与 Compose 组织不受影响。

路由分两类，判别只有一条：请求最终落在**进程**上，还是落在**文件**上。

| 路由类型 | 上游 | nginx 指令 | 现状 |
|---|---|---|---|
| 反向代理 | `web-net` 上的容器 | `proxy_pass` | **当前唯一在用** |
| 静态托管 | 宿主机文件（`apps/<名>/dist`） | `alias` / `root` + `try_files` | 备选，未启用（见 §5.2） |

有进程就必须反代：页面要执行代码、API 要读写数据，这两件事 nginx 做不到。

### 5.2 静态应用托管（`apps/`，备选）

> **当前未启用。** 个人站已改为 SSR（见 §6.2）。本节保留给未来的纯静态站——
> 文档站、作品集快照这类不需要服务端逻辑的东西。启用时按下面的做法走。

静态应用的文件通过**只读绑定挂载**进入入口层容器，nginx 直接读盘返回，全程不经过任何业务容器：

```yaml
# nginx/compose.yml 的 volumes 段
    volumes:
      - ./conf.d:/etc/nginx/conf.d:ro
      - ../apps/docs/dist:/usr/share/nginx/html/docs:ro
```

三个要点：

- 路径相对 **compose 文件所在目录**（`nginx/`），所以是 `../apps/...`，不是在哪个目录敲的命令决定的。
- 容器内挂载点 `/usr/share/nginx/html/<名>` 必须与 `location` 的 URI 前缀**同名**，否则 `try_files` 的兜底会落到别的目录。
- 一个站一行挂载，新增站点不触碰别人的配置行。

路由（`nginx/conf.d/default.conf`）：

```nginx
location /docs/ {
    alias /usr/share/nginx/html/docs/;
    index index.html;
    try_files $uri $uri/ /docs/index.html;   # SPA 兜底；纯静态站可省
}

location = /docs {                            # 静态站只有 GET，可以放心用 301 补斜杠
    return 301 /docs/;
}
```

如果将来用静态方案接管根路径，用 `root` 而非 `alias`：

```nginx
location / {
    root /usr/share/nginx/html/home;
    index index.html;
    try_files $uri $uri/ /index.html;
}
```

根路径用 `alias` 会踩「location 斜杠与 alias 斜杠配对」的老坑，表现为 404 或拼出 `/docs/docs/` 这种路径；`root` 是拼接语义，不会出这个问题。

缓存策略：现代前端构建产物文件名自带内容指纹（`index-a1b2c3.js`），可以长缓存：

```nginx
location ~* \.(js|css|woff2?|png|jpe?g|svg)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}
```

前提是文件名带指纹。`index.html` **不能**套这条规则——它是入口，被缓存一年就等于站点停止更新。

静态托管特有的三个坑，启用前先看：

- **`dist/` 不存在时 Docker 会自动建一个 root 属主的空目录**。挂载路径不存在，Docker 不报错而是创建它——
  结果 nginx 静默返回 404/403，而普通用户之后 `npm run build` 又写不进去。所以**先构建、再起容器**。
- **子路径部署必须配 `base`**。Vite 的 `base: '/docs/'`、Astro 的 `base`、Hugo 的 `baseURL` 尾段，
  都要带上挂载前缀。漏了的话产物里还是写死 `/assets/...`，整站白屏 + 一堆 404，而 HTML 本身返回 200。
- **`alias` 里的 `try_files` 兜底按 `root` 解析，不是按 `alias`**。`/docs/index.html` 能成立，
  前提是文件确实在 `root/docs/` 下——也就是挂载点必须与 URI 前缀同名。

### 5.3 反代配置（`services/`，当前主用）

```nginx
server {
    listen 80;

    # 个人站：整站交给 Astro SSR（页面和 API 都在同一个上游里）
    location / {
        proxy_pass http://site:4321;          # 末尾不带斜杠：URI 原样透传
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 其他服务用更长的前缀，前缀越长越优先，不会被上面的 / 吃掉
    location /hello/ {
        proxy_pass http://hello-api:8000/;    # 带斜杠：剥掉 /hello/ 前缀
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

四个要点：

- 上游写**容器名**，不写 IP；服务重建、容器漂移不影响入口配置。
- `location /` 兜底一切后续路径，所以其他服务必须用更长的前缀。nginx 的前缀匹配取**最长的那条**，
  `/hello/` 会赢过 `/`，与书写顺序无关。
- 接管 `/` 之前要**先删掉** `default.conf` 里那段 `location = /` 的占位响应
  （`return 200 "入口层就绪…"`）。精确匹配优先级高于所有前缀匹配，留着它整站打不开，
  而且返回的是 200 不是 404——排查时最容易误判成"应用没起来"。
- `proxy_pass` 末尾斜杠决定剥不剥前缀：`http://site:4321` 原样透传（整站），
  `http://hello-api:8000/` 把 `/hello/` 换成 `/`（剥前缀）。差一个字符就是 404。

## 6. 服务接入规范

接入分两条路：有常驻进程的走 `services/`，纯静态的走 `apps/`（后者当前未启用）。
两者互不依赖，各自独立。

### 6.1 后端服务接入（`services/`）

服务的 Compose 组织采用**主文件 include 子文件**模式（Compose v2.20+）：总入口只做聚合，不含任何服务定义；每个子服务可独立 `up/down/logs`。

总入口（`<repo>/compose.yml`）：

```yaml
include:
  - ./nginx/compose.yml
  - ./services/site/compose.yml
```

`services/hello-api/` 与 `services/_template/` 一样只作参考样板，**不编入编排**：
它没有业务价值，却要占 256M。需要试跑时把它加回 include，并在 nginx 里补一段
`location`——少这段，nginx 会因 `host not found in upstream` 起不来。

新服务接入动作（唯一的标准路径）：

1. 复制 `services/_template/` 为新服务目录
2. 修改 `compose.yml` 中的服务名、`mem_limit`、网络归属；确需直连调试时才开 `ports:`
3. 在 `default.conf` 增加一段 `location`
4. 端口分配登记至 §8 端口表
5. 在服务目录 `README.md` 记录：用途、访问方式、依赖

服务移除：反向执行以上步骤，其余服务零改动。

服务模板基线（`_template/compose.yml`）：

```yaml
services:
  my-app:
    build: .                     # 纯镜像服务改用 image:
    container_name: my-app       # 服务名 = 容器名 = 内部域名，三者一致
    restart: unless-stopped
    env_file: .env
    networks:
      - web-net
      - db-net                   # 按需保留
    mem_limit: 256m              # 必填，见 §7
    # ports: 默认不声明，统一经入口层

networks:
  web-net:
    external: true
  db-net:
    external: true
```

### 6.2 个人站接入（`services/site`，Astro SSR）

个人站要跑 API、按请求渲染页面，所以按普通服务接入，**不放进 `apps/`**。基座是 `astro-theme-pure`。

1. 代码落到 `services/site/`，目录内自带 `Dockerfile` 与 `compose.yml`
2. `astro.config.ts` 去掉 `@astrojs/vercel`，换成 `@astrojs/node`：

```ts
import node from '@astrojs/node'

export default defineConfig({
  site: 'http://<你的地址>',
  output: 'server',
  adapter: node({ mode: 'standalone' })
})
```

**适配器大版本要和 astro 对齐，别直接装 latest。** 主题把 `astro` 精确锁在 `6.4.8`，
而 `bun add @astrojs/node` 默认装当时的最新版（11.x，peer 要求 `astro ^7.2.1`）。
装错的后果很隐蔽：**构建照样成功、`dist/server` 照样产出，直到启动才报**
`TypeError: app.getLogger is not a function`。判断依据是适配器的 `peerDependencies`，
不是"安装时没报错"。与 astro 6 对齐的是 `@astrojs/node@^10.1.4`（peer `^6.3.0`）。

3. 按需标记渲染方式（见下方「混合渲染」）
4. 加健康端点 `src/pages/healthz.ts`——主题没有，而 compose 的 healthcheck 要它
5. `compose.yml` 按模板写：`container_name: site`、`mem_limit: 256m`、只挂 `web-net`、不声明 `ports`
6. 根 `compose.yml` 的 `include` 加一行
7. `default.conf` 加 `location /`（见 §5.3）
8. 端口登记：容器内 4321，不映射宿主机（见 §8）

`services/site/compose.yml` 基线：

```yaml
services:
  site:
    build: .
    container_name: site
    restart: unless-stopped
    environment:
      NODE_ENV: production
      HOST: 0.0.0.0        # 显式声明：只监听回环的话 nginx 反代直接 502
      PORT: 4321
    networks:
      - web-net
    mem_limit: 256m
    healthcheck:
      # node:22-slim 里没有 wget / curl，用 node 自带的 fetch 探活
      test:
        - CMD
        - node
        - -e
        - "fetch('http://127.0.0.1:4321/healthz').then(r=>process.exit(r.ok?0:1),()=>process.exit(1))"
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 20s    # 比 nginx 长：Node 冷启动要读配置、初始化 sharp

networks:
  web-net:
    external: true
```

两处容易照抄出错的地方：

- **别照搬 nginx 那种 `wget` 探针**。入口层用 `nginx:alpine`，自带 busybox 的 wget；
  运行镜像是 `node:22-slim`，两者都没有。用 `node -e` 调 `fetch` 最省事，不必为此装 curl。
- **`env_file: .env` 要求文件真实存在**，缺了会让整份 compose 解析失败（不像 `environment`
  有默认值兜底）。`site` 目前没有需要外置的配置，先不写；将来加密钥时再建 `.env` 并补这一行。

**混合渲染：别做全站 SSR。** 主题里博客列表、文章、标签这些动态路由页面已经写死
`export const prerender = true`，构建期就生成 HTML，Pagefind 索引照常可用。你只需要给自己加的东西标方向：

```ts
// src/pages/api/contact.ts —— 需要运行时
export const prerender = false
export const POST = async ({ request }) => { /* ... */ }

// src/pages/photos.astro —— 纯静态内容，交给构建期
export const prerender = true
```

**默认值会随 `output` 翻转**：`output: 'static'` 下默认预渲染，`output: 'server'` 下默认按请求渲染。
不写 `prerender` 的页面每次访问都会执行一遍。

构建产物是两份，都要进镜像：

```
dist/client/     # HTML、CSS、JS、图片等静态资源
dist/server/     # SSR 入口 entry.mjs 与服务端 bundle
```

只拷 `dist/client` 的镜像能启动，但每个请求 500。

**包管理器别混用**：主题仓库只带 `bun.lock`，没有 `package-lock.json`，镜像里 `npm ci` 会直接失败。
用 `oven/bun:1-alpine` 跑 `bun install --frozen-lockfile`，或者先 `bun install` 生成
`package-lock.json` 再回退到 npm——选一条走到底。

### 6.3 纯静态站接入（`apps/`，备选）

当前没有静态站，这是保留路径。启用时：

1. `apps/<名>/` 放源码，构建产物输出到 `dist/`
2. `nginx/compose.yml` 的 `volumes` 加一行只读挂载
3. `default.conf` 加 `location`（写法见 §5.2）
4. 端口不登记，复用 80
5. 目录 `README.md` 记录用途、访问路径、构建命令

宿主机不装 Node，构建在一次性容器里做；产物不入库（`dist/` 已在 `.gitignore`）：

```bash
docker run --rm --memory=1g \
  -v "$PWD/apps/docs:/app" -w /app \
  -e npm_config_registry=https://registry.npmmirror.com \
  node:22-alpine sh -c "npm ci && npm run build"
```

改 `location` 用 reload；改挂载必须重建容器——`nginx -s reload` 不会重新读 `volumes`。

## 7. 资源模型

2C2G 的可用预算：系统 + Docker 守护进程约占 400~500M，可分配给容器约 **1700M**，必须保留 ≥10% 余量以避免 OOM。

| 服务 | 定位 | mem_limit |
|---|---|---|
| nginx | 入口层 | 128m |
| site（Astro SSR） | 个人站：页面 + API | 256m |
| hello-api（示例） | 参考样板，未编入编排、不启动 | 0 |
| postgres:17 | 关系型数据库 | 512m |
| redis:alpine | 缓存/中间件 | 128m |
| adminer | 数据库管理界面（模板未部署） | 64m |
| **预留余量** | 新接入的业务服务 | **~610m** |

容量约束：

- 任何服务 `mem_limit` 必填；未声明上限的服务不允许进入部署。
- 新服务接入前先评估剩余预算，预算不足则先砍容量或下线低价值服务。
- **`site` 实测空闲约 62MB，`mem_limit` 给 256m。** 余量不算浪费：图片按需处理、
  并发请求都会短时抬高占用，贴着实测值设限等于给 OOM 留了个口子。
  真正吃内存的是构建：Astro + sharp + Pagefind 的峰值可达 1.5~2G，而构建不受 `mem_limit` 管束
  （它是一次性 `docker build`，不是服务）。在 2C2G 的生产机上构建前先
  `docker compose stop postgres redis` 把 640M 腾出来，构建完再 `up -d` 复原。
  否则构建进程和数据库抢内存，内核会挑一个杀掉——通常是 postgres。
- PostgreSQL 以受限参数运行以兑现其 512M 预算（compose 里用 `-c` 传入）：

```ini
shared_buffers=128MB
work_mem=4MB
max_connections=50
```

磁盘同属受限资源：构建垃圾需纳入例行管理（`docker system prune`），持久化数据收敛于 `data/` 便于观察占用。

## 9. 关键取舍与已知陷阱

前面的章节写"结构是什么"，这一节写"为什么这么定"，以及实际踩过的坑。
每条都附了代价——没有只赚不赔的选择。

### 9.1 后端技术栈不锁定

模板不自带"必须是 Go / 必须是 Node"的约束。示例服务 `hello-api`（现为参考样板，
未编入编排）用 Go，
只是因为 2C2G 下它的镜像（19.7 MB）与常驻内存（约 1.3 MiB）最小。
换成 Node、Python 都不影响入口层与网络模型——服务之间只靠 HTTP + 容器名耦合，
不共享任何语言层面的东西。

**代价**：技术栈分散会增加维护负担，基础镜像与构建缓存的复用率下降。
团队固定一种语言时，建议把 `services/_template` 直接改成对应语言的骨架。

### 9.2 为什么统一在根目录启停

各服务固定了 `container_name`（为了给反代一个稳定的 DNS 名），副作用是
同一个服务不能在两个 compose 项目里各起一份——容器名会冲突。
所以约定：日常在根目录操作；单服务调试前先 `docker compose down` 掉根项目。

**代价**：不能横向扩容（多副本会撞名）。单机单副本场景可以接受；
真要多副本，必须去掉 `container_name`，改用 compose 给服务名自动注册的网络别名。

### 9.3 为什么是 PostgreSQL 而不是 MySQL

| 维度 | PostgreSQL 17 | MySQL 8.0 |
|---|---|---|
| 镜像体积（实测） | 424 MB | 1.1 GB |
| 同 512m 额度下常驻内存（实测） | 57 MiB | 137 MiB |
| 跨库查询 | 需 dblink / fdw，按库隔离更硬 | 同实例内可直接跨库查 |
| 中文全文检索 | 需装 zhparser / pg_jieba 并编译 | 内置 ngram 分词 |

对 2C2G 的目标机来说，前两行是决定性的。

**代价**：中文全文检索要额外装扩展；工具链与 MySQL 不同（端口 5432、
客户端 `psql`、库内还有 schema 一层），跟习惯 MySQL 的人协作要额外说明。

### 9.4 构建依赖一律走国内镜像

pip、npm、Go module 直连官方源在目标网络下基本不可用——实测 pip 光拉几个包的
元数据就要 60 秒以上，构建会在超时处反复中断。三个 Dockerfile 都把源做成
可覆盖的构建参数，默认指向国内镜像：

| 生态 | 参数 | 默认值 |
|---|---|---|
| pip | `PIP_INDEX_URL` | `mirrors.aliyun.com/pypi/simple` |
| npm | `NPM_REGISTRY` | `registry.npmmirror.com` |
| Go | `GOPROXY` | `goproxy.cn` |

需要官方源时用 `--build-arg` 覆盖，不必改文件。

### 9.5 已知陷阱

- **`depends_on` 不保证依赖就绪**，只保证启动顺序。连数据库的服务必须自己轮询等待，
  并把错误分类：密码错、库不存在这类配置问题立刻失败，连接被拒才重试。
- **301 会把 POST 变成 GET**。补斜杠只适用于纯读路由；有写操作的路径不能靠重定向
  "纠正"，否则写操作会悄悄变成读操作，而且不报错。
- **`proxy_pass` 末尾的斜杠决定要不要剥前缀**。带斜杠则替换掉 location 匹配的部分，
  不带则原样透传，差一个字符就是 404。
- **`docker compose config --services` 不校验 `.env`**，它只列服务名；
  要 `docker compose config` 才会去解析 `env_file`。
- **容器写入的文件属主是镜像内的 uid**（postgres 是 70、redis 是 999），
  宿主机普通用户删不掉，清理 `data/` 需要 `sudo`。
- **重建被反代的服务后要 reload nginx**。nginx 只在加载配置时解析一次上游域名并缓存 IP，
  容器换了 IP 就会 502。
- **nginx 启动时要解析所有 upstream**，任何一个容器没起就直接 `host not found in upstream`，
  进程退出并被重启策略拉起来反复重试。所以加一段 `location` 等于给 nginx 增加一条启动硬依赖；
  下线某个服务时，必须同步删掉它那段 `location`。
- **改完 Go 依赖要 `go mod tidy`**。`go get` 只落直接依赖，间接依赖不进 `go.sum`，
  构建会报 `missing go.sum entry`。
- **`dist/client` 和 `dist/server` 要一起进镜像**。SSR 构建产出两份，服务入口是
  `dist/server/entry.mjs`。只拷 `client` 的镜像能启动，但每个请求 500。
- **能构建 ≠ 能启动**。适配器与 `astro` 的 peer 不匹配时，`astro build` 全绿、产物齐全，
  直到 `node ./dist/server/entry.mjs` 才炸，例如 `app.getLogger is not a function`。
  装适配器前先看它的 `peerDependencies`，别信 "latest"。
- **正文里的远程图片会让构建依赖外部 CDN**。Astro 要在构建期下载它来推算宽高（`inferSize`）
  并做优化，CDN 抖一下就是 `Failed to parse image reference`——而且这个 `catch` 会把真实原因
  吞成一句笼统的报错。要么把图片放进 `src/assets/` 或 `public/`，要么接受构建不稳定。
- **`output: 'server'` 下不写 `prerender` 的页面是动态的**。默认值随 output 翻转：
  `static` 默认预渲染，`server` 默认按请求渲染。主题的动态路由已显式 `prerender = true`，
  自己新加的页面要明确选边，别默认落在运行时。
- **服务端渲染的组件里没有 `window`**。`localStorage`、`document` 只能在 `<script>` 里访问；
  写在前言或模板表达式里，会在请求期报 `window is not defined`，而本地 `astro dev` 未必暴露。
- **`sharp` 是原生依赖**。构建镜像与运行镜像的 CPU 架构必须一致，否则容器起来后报
  `invalid ELF header`——跨架构构建（arm 机器构建给 x86 服务器）最容易撞。
- **健康检查要打应用自己的端点**，不是打 nginx。`site` 的 healthcheck 用容器内
  `wget http://127.0.0.1:4321/healthz`；只探 nginx 的话，应用挂了容器仍显示 healthy。
- **`nginx -s reload` 不会重新读挂载**。改 `volumes` 必须
  `docker compose up -d nginx` 重建容器；只有改 `conf.d` 里的内容才能靠 reload 生效。

### 9.6 为什么个人站最终做成 SSR 服务

这套方案最初定的是纯静态托管（`apps/`），理由很硬：2C2G 下"不新增进程"最省，
静态站点常驻内存是 0。如果这个站只是个博客，那个判断依然成立。

**变的是需求**：站上要放自定义页面和 API。一旦有 API，静态方案就得再起一个服务专门放接口，
于是变成两套部署、两份配置、一次跨域处理，还要维护"前端构建"和"接口发布"两条流水线。
省下的那 150MB，换来的是更多的拼装成本——**把页面和接口放回同一个进程，反而是简化**。

所以现在走 SSR。成本是明面上的三条：

- 多一个常驻进程，约 100~150MB，`mem_limit` 256m。
- 多一个有**执行入口**的攻击面。以前 nginx 只读文件，现在请求能触发代码、能碰数据库，
  API 的输入校验、限流、鉴权从此是必需品，不是加分项。
- 构建更重：Pagefind 索引加 sharp 图像处理，峰值 1.5~2G，2C2G 上要先停数据服务再构建（见 §7）。

压低成本靠**混合渲染**，不是全站 SSR：博客列表、文章、标签这些在构建期就生成 HTML，
运行时只处理 API 和少数动态页（见 §6.2）。架构上它是"大部分静态、局部动态"，
但**部署形态是服务**——这一点决定了它必须进 `services/`。

**什么时候该退回去**：如果那些 API 最后只剩一两个表单，或者根本不需要服务端逻辑，
把 `site` 换回静态产物加一个极小的接口服务，仍然更省。届时 `apps/` 这条路径还在（§5.2、§6.3）。

### 9.7 密码怎么生成、怎么轮换

`.env` 里的密码不是手写的，用一条命令生成：

```bash
openssl rand -base64 24 | tr -dc "A-Za-z0-9" | head -c 24
```

| 步骤 | 作用 |
|---|---|
| `openssl rand -base64 24` | 取 24 字节（192 bit）随机数，base64 后是 32 个字符 |
| `tr -dc "A-Za-z0-9"` | 删掉 `+` `/` `=`：它们进 `DATABASE_URL` 需要 URL 编码，`=` 还会被当成变量分隔 |
| `head -c 24` | 截到 24 位 |

字符集 62 个、长度 24，约 143 bit 熵——这个量级下暴力破解没有意义。

存放：`.env` 权限 `600`（仅属主可读），已被 `.gitignore` 排除；
仓库里只有 `.env.example`，值一律是 `change-me`。

**轮换不是改 `.env` 就完事。** `POSTGRES_*` 与 `APP_PASSWORD`
只在 `data/postgres/` 为空、首次初始化时生效，之后改文件对库里的密码没有影响。
换密码必须进库执行：

```sql
ALTER ROLE app      WITH PASSWORD '新密码';
ALTER ROLE postgres WITH PASSWORD '新密码';
```

再同步 `.env` 以及所有用到该密码的服务配置，重启对应容器。

**边界**：这是开发环境的做法。生产环境不该让密码落在 `.env` 或环境变量里
（`docker inspect` 就能看到），应改用 Docker secrets、云厂商 KMS 或 Vault。

## 10. 演进路径

| 触发条件 | 架构动作 | 不变项 |
|---|---|---|
| 引入域名 | 入口层改为按子域名分发，增加 TLS（Caddy 或 Nginx+ACME） | 目录结构、Compose 组织、网络分域 |
| 静态页访问量变大 | nginx 直接托管 `dist/client`，只把 API 与动态路由反代给 Node | 目录结构、网络分域 |
| 需要评论 | 增加 waline 服务，复用 postgres | 内存预算再扣 ~100M |
| 需要可用性观测 | 增加轻量探活组件（如 uptime-kuma，~100M） | 不引入 Prometheus 全家桶（超出内存预算） |
| 数据产生保留价值 | 最小备份：打包 `data/` 至对象存储 | 仍是单机，不做容灾 |
| 内存不足 | 原地升配（2G→4G） | 架构零改动，仅放宽 §7 预算表 |
