## 1. 都在传输层，差别在哪

IP 负责把包送到主机，TCP 和 UDP 负责把包送到主机上的某个进程，靠的是端口号。

两者最根本的差别是一句话：**TCP 建立连接、保证有序可靠，UDP 发出去就不管了**。其余区别都是从这一条派生出来的。

| 维度 | TCP | UDP |
| :--- | :--- | :--- |
| 连接 | 三次握手建立，四次挥手断开 | 无连接，直接发 |
| 可靠性 | 确认 + 重传，丢包会补 | 不保证送达 |
| 有序性 | 按序交付，乱序会重排 | 不保证顺序 |
| 消息边界 | 字节流，没有边界 | 保留边界，一次发一次收 |
| 流量控制 | 滑动窗口，接收方通告 | 无 |
| 拥塞控制 | 有，慢启动 + 拥塞避免 | 无（QUIC 在应用层补） |
| 头部开销 | 20 字节起，最多 60 | 固定 8 字节 |
| 传输方式 | 点对点 | 点对点、广播、组播 |
| 典型协议 | HTTP/1.1、HTTP/2、SSH、MySQL | DNS、DHCP、QUIC、视频流 |

## 2. 连接：三次握手

握手的核心是**同步双方的初始序列号**，以及**防止网络里滞留的旧连接被误建立**。确认双方能收能发是顺带的结果。

| 步骤 | 方向 | 报文 | 关键字段 |
| :--- | :--- | :--- | :--- |
| 1 | 客户端 → 服务端 | SYN | `seq=x` |
| 2 | 服务端 → 客户端 | SYN + ACK | `seq=y`，`ack=x+1` |
| 3 | 客户端 → 服务端 | ACK | `ack=y+1` |

完成后双方进入 `ESTABLISHED`，可以开始传数据。服务端在收到第三个 ACK 之前处于 `SYN_RCVD`，连接放在半连接队列里。

**为什么不是两次。** 只握手两次，服务端无法确认「客户端能收到我的报文」，序列号只同步了一个方向。更实际的问题是历史连接：网络里滞留的旧 SYN 到达服务端，两次握手会直接建立一个错误的连接，客户端根本不知道；三次握手里，客户端不会为这个旧 SYN 回第三个 ACK，服务端等不到就放弃了。

**为什么不是四次。** 第二步把 SYN 和 ACK 合在一个报文里发了，省一次往返。

**SYN Flood** 利用的正是半连接队列：攻击者发大量 SYN 不回 ACK，把队列占满。`net.ipv4.tcp_syncookies` 是常见的缓解手段，值为 1 时表示开启。

## 3. 断开：四次挥手与 TIME_WAIT

TCP 是全双工的，两个方向要分别关闭，所以是四次。

| 步骤 | 方向 | 报文 | 含义 |
| :--- | :--- | :--- | :--- |
| 1 | 主动方 → 被动方 | FIN | 我没数据要发了 |
| 2 | 被动方 → 主动方 | ACK | 收到，但我可能还有数据要发 |
| 3 | 被动方 → 主动方 | FIN | 我也发完了 |
| 4 | 主动方 → 被动方 | ACK | 收到，进入 TIME_WAIT |

第二步和第三步之间，被动方还能继续发数据，这叫**半关闭**。主动方收到 FIN 后进入 `CLOSE_WAIT` 的是被动方，主动方则停在 `FIN_WAIT_2` 等对方的 FIN。

**TIME_WAIT 要等 2MSL（Linux 上约 60 秒）**，原因有两个：

1. 最后一个 ACK 可能丢。丢了的话对方会重发 FIN，还在 TIME_WAIT 的这端能再回一次 ACK。如果直接关掉，对方只能收到 RST。
2. 让这条连接上的旧报文在网络里彻底消散，避免它们混进后面复用相同四元组的新连接。

在机器上看连接状态：

```bash
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn

#   25 ESTAB
#   19 LISTEN
#    1 SYN-SENT
```

短连接多的服务会看到大量 `TIME-WAIT`，一般是客户端或服务端频繁建连导致的。缓解方向是复用连接（keep-alive、连接池），而不是先调参数。

## 4. 可靠性：序号、确认、重传

TCP 给每个字节编号。接收方回 ACK 时带的是**期望收到的下一个序号**，表示这之前的所有字节都收到了，这叫累计确认。

丢包靠两种方式发现：

**超时重传。** 发送方为一个报文启动定时器，超时没收到 ACK 就重发。超时时间 RTO 由 RTT 估算得来，不是固定值。

**快速重传。** 接收方收到乱序报文时，会重复发送同一个 ACK。发送方连续收到 **3 个重复 ACK**，就认为中间那个丢了，不等超时直接重传。

快速重传只补一个包。如果一次丢了多个，发送方不知道后面还缺哪些，只能一个个试。**SACK（选择确认）** 让接收方在 ACK 里附带「我已经收到了哪些区间」，发送方据此只重传真正缺失的部分。

**TCP 保证的是「可靠、有序」，不是「一定送达」。** 连接断了、重试超时了，应用层拿到的是错误，不是数据。

## 5. 边界：字节流与数据报

TCP 是字节流，没有消息边界。发送方 `write` 两次，接收方可能一次 `read` 到两段拼在一起，也可能一段分成两次到——这就是常说的**粘包**（其实不是 TCP 粘的，是应用层没定义边界）。

解决办法是在应用层自己划界：

| 方式 | 做法 | 例子 |
| :--- | :--- | :--- |
| 长度前缀 | 先发 4 字节表示长度，再发内容 | 多数二进制协议、gRPC |
| 分隔符 | 用固定字符分隔 | HTTP 头用 `\r\n\r\n`，Redis 协议 |
| 定长 | 每条消息固定长度 | 部分游戏协议 |

UDP 保留边界：一次 `sendto` 对应一次 `recvfrom`，收到的就是完整的一条。代价是这条可能丢、可能乱序、可能重复，应用层要自己处理。

**UDP 的报文长度受 MTU 限制。** 以太网 MTU 1500，减去 IP 头 20 和 UDP 头 8，单个 UDP 载荷最多 1472 字节。超过会在 IP 层分片，任一分片丢失整个报文就废了，所以大文件不要直接用 UDP 发。

## 6. 流量控制与拥塞控制

两个容易混的概念，作用对象不同：

| | 流量控制 | 拥塞控制 |
| :--- | :--- | :--- |
| 保护谁 | 接收方，别把它缓冲区撑爆 | 网络，别把链路压垮 |
| 靠什么 | 接收窗口 `rwnd`，接收方在 ACK 里通告 | 拥塞窗口 `cwnd`，发送方自己维护 |
| 实际发送量 | `min(rwnd, cwnd)` | 同左 |

**流量控制**是滑动窗口：接收方告诉发送方「我还能收多少」，窗口为 0 时发送方停止发送，定期发探测报文问什么时候能继续。

**拥塞控制**分四个阶段：

1. **慢启动**：`cwnd` 从很小开始，每收到一个 ACK 就加一倍，指数增长。
2. **拥塞避免**：`cwnd` 超过 `ssthresh` 后改为每个 RTT 加一，线性增长。
3. **快重传**：收到 3 个重复 ACK 立即重传，不等超时。
4. **快恢复**：快重传后把 `ssthresh` 和 `cwnd` 减半，直接进入拥塞避免，而不是回到慢启动。

超时重传则会认为网络严重拥塞，`cwnd` 直接降到 1，重新慢启动。

Linux 默认的拥塞控制算法是 CUBIC：

```bash
sysctl net.ipv4.tcp_congestion_control
# net.ipv4.tcp_congestion_control = cubic
```
BBR 不依赖丢包判断拥塞，在高丢包长链路上表现更好，需要在系统里显式切换。

**UDP 两个都没有。** 这既是它快的原因，也是它在公网上容易把别人挤掉的原因。QUIC 在 UDP 之上自己实现了确认、重传和拥塞控制，等于把 TCP 的活搬到了用户态。

## 7. 包头对比

**TCP 头部最小 20 字节，带选项最多 60 字节：**

| 字段 | 长度 | 作用 |
| :--- | :--- | :--- |
| 源端口 / 目的端口 | 各 2 字节 | 定位进程 |
| 序号 | 4 字节 | 字节编号 |
| 确认号 | 4 字节 | 期望收到的下一个序号 |
| 数据偏移 | 4 位 | 头部长度 |
| 标志位 | 9 位 | SYN、ACK、FIN、RST、PSH、URG 等 |
| 窗口 | 2 字节 | 接收窗口 `rwnd` |
| 校验和 | 2 字节 | 覆盖头部和数据 |
| 紧急指针 | 2 字节 | 配合 URG |
| 选项 | 0~40 字节 | MSS、SACK、时间戳、窗口扩大 |

**UDP 头部固定 8 字节，只有四个字段：**

| 字段 | 长度 |
| :--- | :--- |
| 源端口 | 2 字节 |
| 目的端口 | 2 字节 |
| 长度 | 2 字节 |
| 校验和 | 2 字节 |

开销差多少，算一下就清楚。MTU 1500 时：

- TCP：1500 − 20（IP）− 20（TCP）= **1460 字节**有效载荷
- UDP：1500 − 20（IP）− 8（UDP）= **1472 字节**

单包差 12 字节，占比不到 1%。**头部开销通常不是选 UDP 的理由**，真正的原因是省掉握手和重传逻辑。

## 8. 怎么选

| 场景 | 选择 | 原因 |
| :--- | :--- | :--- |
| 网页、API、文件传输 | TCP | 数据不能缺，顺序不能乱 |
| 数据库连接 | TCP | 同上，且连接有状态 |
| DNS 查询 | UDP 为主 | 一问一答，包小，省握手 |
| DNS 响应超过 512 字节 | 转 TCP | UDP 报文被截断，需要完整结果 |
| 视频通话、直播 | UDP | 晚到的帧没意义，宁可丢也不等 |
| 实时游戏 | UDP | 状态以最新为准，重传旧包反而添乱 |
| 大文件、可靠传输 | TCP | UDP 要自己实现重传，等于重写 TCP |
| HTTP/3 | UDP（QUIC） | 在 UDP 上实现可靠传输，避开 TCP 的队头阻塞 |

**HTTP/3 值得单独提一句。** 它不是「UDP 不可靠所以不能用」，而是在 UDP 之上用 QUIC 重新实现了可靠传输、加密和拥塞控制，顺便解决了 TCP 的队头阻塞——一个包丢了，HTTP/2 的所有流都要等，QUIC 只影响那一条流。

**UDP 快，快在省掉握手和确认。** 公网上没有重传和拥塞控制，丢包严重时会把链路越挤越死，实际体验可能比 TCP 更差，所以主流实时方案（QUIC、WebRTC）都在 UDP 之上自己实现了拥塞控制。
