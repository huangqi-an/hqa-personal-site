按一次 Ctrl+F5，页面立刻快一截；有时按了却毫无变化，甚至比之前更慢。缓存的规则本身不复杂，只是浏览器替你做决定的过程看不见：这个请求到底要不要发出去。

判断只有三步：本地有没有副本、副本够不够新、不新的话能不能只问服务器一句。这篇按这三步展开，顺带把 `Cache-Control` 那一串指令各自管哪一段对应上。

## 缓存省下的是一次往返

缓存的价值不是「更快」，而是**这个请求根本没发出去**。

一次同城往返 20~50ms，跨洋 150ms 起。一个页面几十个静态资源，每个都走一趟，累加出来就是秒级差距。带宽通常不是瓶颈，往返次数才是。

所以同一份资源，只有三种结局：

| 结局 | 请求发出去了吗 | 状态码 | 代价 |
|---|---|---|---|
| 本地没有副本 | 发了 | `200` | 一次完整往返，外加整个 body |
| 有副本，且还新鲜 | **没发** | `200`（浏览器合成） | 零往返 |
| 有副本，但已过期 | 发了条件请求 | `304` 或 `200` | 一次往返，通常没有 body |

后面几节都在解释一件事：什么条件下走到哪一行。

## 新鲜度：缓存自己就能回答的问题

能不能直接用，只看一个不等式：**当前年龄 < 新鲜期**。这个判断完全在本地完成，不需要问服务器。

```
age      = now - Date + Age
lifetime = max-age
```

- **新鲜期**来自 `max-age`（秒）。没有它就看 `Expires`（绝对时间）；两者都有时 `max-age` 优先，因为 `Expires` 会被客户端时钟带偏。
- **当前年龄**从响应生成的 `Date` 起算，不是从浏览器收到的那一刻。中间如果经过共享缓存，还要加上它返回的 `Age`。
- 过期不等于删除。条目还在磁盘上，只是进入了「需要校验」的状态。

举个具体数字：响应头 `Date: 10:00:00`、`Cache-Control: max-age=600`，浏览器在 10:04 收到它时，年龄是 240 秒，还剩 360 秒新鲜期。如果中间经过一层缓存，它返回 `Age: 300`，那浏览器拿到手时只剩 300 秒。

### 没有 max-age 时：启发式缓存

响应里既没有 `max-age` 也没有 `Expires`，但有 `Last-Modified` 时，缓存会自己估一个新鲜期：常见实现取 `(Date - Last-Modified)` 的 10%。

这是 Chrome、Firefox 的实现惯例，规范只允许启发式，没有规定比例。不想让缓存替你猜，就显式写 `max-age`。

## 不新鲜了：条件请求与 304

过期只意味着要问一次，不意味着要重新下载。

两个校验器对应两个请求头：

| 响应头 | 下次请求带 | 判断依据 |
|---|---|---|
| `ETag: "d4e5f6"` | `If-None-Match: "d4e5f6"` | 内容标识是否变化 |
| `Last-Modified` | `If-Modified-Since` | 修改时间是否变化 |

两个请求头同时出现时，服务器必须忽略 `If-Modified-Since`，只按 `If-None-Match` 判断。

```http
GET /index.html HTTP/1.1
Host: example.com
If-None-Match: "d4e5f6"
If-Modified-Since: Wed, 27 Sep 2023 10:00:00 GMT

HTTP/1.1 304 Not Modified
Cache-Control: no-cache
ETag: "d4e5f6"
Date: Wed, 27 Sep 2023 12:30:00 GMT
```

**304 没有 body。** 浏览器拿到它之后做三件事：用本地副本渲染、用 304 的头部更新已存条目（包括新的 `Date`）、按更新后的头部重新计算新鲜期。如果 `ETag` 变了，服务器直接回 `200` 和新内容，走的是另一条路。

`ETag` 与 `Last-Modified` 的分工：

| | `ETag` | `Last-Modified` |
|---|---|---|
| 精度 | 内容级 | 秒级 |
| 弱校验 | `W/"x"` 表示语义等价即可 | 没有这个概念 |
| 依赖 | 服务器自己生成 | 文件修改时间 |
| 弱点 | 需要额外计算 | 同一秒内多次修改无法区分；拷贝、回滚会让时间失真 |

`Last-Modified` 只到秒，两次修改落在同一秒里，就可能错误地返回 304。所以能生成 `ETag` 时优先用它。

那什么情况下只有 `Last-Modified` 也够用？服务器直接托管静态文件时，修改时间天然存在，不必额外计算哈希。Nginx 默认发的 `ETag` 就是由修改时间和文件大小拼出来的，不是内容哈希，本质上仍然属于时间戳那一类信息。只要内容变更不频繁、同一秒内不会被改两次，用时间校验代价更低。

### 「强缓存 / 协商缓存」是社区叫法

规范里只有 freshness（新鲜度）和 validation（校验），没有「强缓存」「协商缓存」这两个词。它们是中文社区为了好记造的对应说法：强缓存指新鲜期内直接用、不发请求；协商缓存指过期后带校验器问一次。

概念没错，但别把它们当成 HTTP 术语去搜规范原文。

## 缓存键与可见范围

缓存不是按 URL 存一份，而是按**键**存一份。键默认是 URL，`Vary` 决定还要把哪些请求头的值算进去。

```http
HTTP/1.1 200 OK
Vary: Accept-Encoding
```

这条声明告诉缓存：同一个 URL，压缩版和未压缩版要分开存。漏写它，服务器给 A 用户返回了 br 压缩的内容，缓存可能把它转给不支持 br 的客户端，页面直接乱码。`Vary: *` 则表示「任何请求都不能复用」，等于放弃缓存；列的字段越多，命中率越低。

判断一个响应能不能复用，缓存实际比较的是「URL + `Vary` 里列出的每个头的值」。所以同一个地址在缓存里可能躺着好几份副本，各自对应不同的请求头组合。

谁能存这份副本，由另外几个指令决定：

| 指令 | 作用 |
|---|---|
| `public` | 明确允许共享缓存（CDN、代理）存，不是「内容公开可见」 |
| `private` | 只允许浏览器这类私有缓存存 |
| `s-maxage` | 只对共享缓存生效，优先于 `max-age`，并隐含 `proxy-revalidate` |

`s-maxage` 对浏览器自己的缓存不起作用。想让两端用不同时长，才需要它。

这也解释了一个常见疑问：经过 CDN 的响应，浏览器看到的 `max-age` 好像变短了。其实是 `Age` 已经有值，新鲜期被扣掉了一段。

## 指令地图：八个指令各管一段

这些指令不是同义词堆，它们回答四个不同的问题：

1. **能不能存？** `no-store`、`no-cache`
2. **能存多久？** `max-age`、`s-maxage`、`Expires`
3. **过期之后怎么办？** `must-revalidate`、`stale-while-revalidate`、`immutable`
4. **谁能存？** `public`、`private`

| 指令 | 回答的问题 | 一句话 |
|---|---|---|
| `no-store` | 能不能存 | 完全不存，内存和磁盘都不留 |
| `no-cache` | 能不能存 | 可以存，但每次复用前必须校验 |
| `max-age=600` | 存多久 | 600 秒内算新鲜 |
| `s-maxage=600` | 存多久（共享缓存） | 只对 CDN / 代理生效，优先于 `max-age` |
| `must-revalidate` | 过期后 | 禁止使用陈旧副本，必须校验成功 |
| `stale-while-revalidate=60` | 过期后 | 过期后 60 秒内先回旧副本，同时后台校验 |
| `immutable` | 过期前 | 新鲜期内即使用户刷新也不发条件请求 |
| `public` / `private` | 谁能存 | 共享缓存 / 只有浏览器 |

三组最容易记反的：

**`no-store` 与 `no-cache`。** 前者是「不存」，后者是「存，但每次用之前问一句」。把 `no-cache` 说成不缓存，是这类问题里最常见的错。

**`must-revalidate` 与 `stale-while-revalidate`。** 方向相反：一个禁止用旧副本，一个允许先用旧副本、后台再校验。

后者适合「旧一点也能看」的内容：商品列表、文章摘要这类页面，过期后先返回缓存里的旧版本，同时后台拉新，下次访问就是新的。代价是用户可能看到几十秒前的数据，所以不适合库存、余额。

**`immutable`。** 它不延长新鲜期，只省掉「新鲜期内用户刷新时的条件请求」。所以它必须和足够长的 `max-age` 一起用，也只对带指纹的资源成立。

```http
GET /assets/app.a1b2c3.js HTTP/1.1
Host: example.com
Accept-Encoding: gzip, br

HTTP/1.1 200 OK
Cache-Control: public, max-age=31536000, immutable
ETag: "a1b2c3"
Vary: Accept-Encoding
Content-Encoding: br
Content-Length: 48213
```

一年有效期敢这么给，前提是文件名里有内容指纹：内容一变，文件名就变，旧的这份永远不会被覆盖。

第二次访问同一地址时，**没有报文可看**。请求根本没发出去，浏览器在发出之前就返回了，Network 面板显示 `200 (from disk cache)`，耗时接近 0ms。那个 `200` 是浏览器为了面板统一而合成的，不代表服务器返回过什么。

## 三类资源，三套策略

策略不是给「网站」定的，是给「一类 URL」定的：

| 资源 | 例子 | 建议 | 理由 |
|---|---|---|---|
| HTML 入口 | `/index.html` | `no-cache` | 每次校验；否则新版本发不出去 |
| 带指纹的静态资源 | `/assets/app.a1b2c3.js` | `max-age=31536000, immutable` | 内容变则文件名变，旧文件可以一直躺着 |
| 接口数据 | `/api/posts` | `no-store` 或很短的 `max-age` | 时效性强，缓存策略要显式声明 |

接口这一类最容易被忽略。不少接口没有显式 `Cache-Control`，GET 响应又带 `Last-Modified`，浏览器就可能按启发式规则缓存一份，于是「数据改了，刷新却没变」。与其事后排查，不如显式写 `no-store`，把决定权拿回来。

为什么不干脆给 HTML 也加一年缓存？因为入口文件是唯一能把新版本「推」给用户的通道。HTML 一旦被长期缓存，用户会一直打开旧页面，而旧页面引用的接口可能已经改了结构——表现为「别人都好了，就我这儿报错」，且清缓存才能恢复。
这三行互相咬合。HTML 短缓存，保证用户下次打开能拿到新版本；静态资源长缓存，靠文件名指纹兜底。发版时老 HTML 还在某个用户的缓存里，它引用的旧文件仍然存在（只要部署时不删旧产物），所以不会白屏；新 HTML 拿到的是新文件名，命中率不受影响。

## 常见误判

**`no-cache` 表示不缓存。** 它允许存储，只是每次复用前必须向源站校验。真正不存的是 `no-store`。

**`immutable` 就是永久缓存。** 它只影响新鲜期内是否发条件请求，不延长新鲜期；过期后照常校验。

**`max-age=3600` 就是一小时后过期。** 新鲜期从 `Date` 起算，经过共享缓存还要叠加 `Age`，浏览器拿到手时可能只剩几分钟。

**返回 304 说明内容没变。** 只能说校验器没变。弱校验（`W/"x"`）下，语义等价就返回 304，字节仍可能不同。

## 小结

- 新鲜期内不发请求，过期后发条件请求；判断式只有一条 `age < lifetime`。
- 304 没有 body，用本地副本，同时刷新已存条目的头部与新鲜期。
- 缓存键是 URL 加上 `Vary` 声明的头；`private` / `public` 决定谁能存。
- 策略按资源类别定：HTML 短、指纹资源长、接口按需。
