这台机器是 2 核 2G 的轻量云服务器，跑着一个个人站，外加一套随时可以加服务的基础设施。
写这篇不是为了推荐某个方案，而是把"为什么这么定"和"哪里卡过"记下来——后者通常更难查。

## 三层

结构很普通，分三层：

```text
浏览器 → nginx :80 → site(Astro) :4321 → postgres / redis（仅内部网络）
```

**入口层**是 nginx，唯一对外的一层。它把 `/` 整站转给 Astro，其他服务按更长的路径前缀分流。
容器只接 `web-net`，碰不到数据库所在的 `db-net`。

**应用层**是 Astro，跑在 Node 里。页面和接口在同一个进程里，省掉跨服务调用和跨域配置。

**数据层**是 PostgreSQL 和 Redis，都不映射宿主机端口，公网只能通过应用间接访问。

三层之间只靠 HTTP 和容器名耦合。服务名固定成容器名，反代直接写 `http://site:4321`，
不写 IP——容器重建后 IP 会变，名字不会。

## 编排：一个服务一个目录

根目录的 `compose.yml` 只做聚合，本身不含任何服务定义：

```yaml
include:
  - ./nginx/compose.yml
  - ./services/site/compose.yml
  - ./services/postgres/compose.yml
  - ./services/redis/compose.yml
```

每个目录里有一套完整的 `compose.yml`，可以单独 `up` 起来调试，也可以被总入口合并。
加一个服务就是加一行 include，删一个服务就是删一行，互不牵连。

所有服务都固定了 `container_name`，好处是反代有稳定的 DNS 名，坏处是不能横向扩容——
两个 compose 项目起同一个服务会撞名。单机单副本的场景下，这个交换划算。

## 静态还是 SSR：来回了一次

一开始定的是纯静态：构建完把 `dist/` 交给 nginx 直接托管，零常驻内存，对 2G 内存来说最省。
如果这个站只是个博客，那个判断到今天依然成立。

改主意是因为要加接口。一旦需要 API，纯静态就得再单独起一个服务放接口，于是变成两套部署、
两份配置、一次跨域，还要维护"页面构建"和"接口发布"两条流水线。
省下的那一百多 MB，换来的是更多的拼装成本——把页面和接口放回同一个进程，反而是简化。

所以现在整站是 SSR。但**部署形态是服务，不等于每个请求都要跑一遍服务端**。

## 混合渲染

Astro 支持按页面决定渲染方式：

```ts
export const prerender = true   // 构建期生成 HTML
export const prerender = false  // 每次请求都渲染
```

博客列表、文章页、标签页、归档页全部 `prerender = true`，构建时就变成静态 HTML，
运行时不占 CPU；只有真正需要计算的接口和少数页面才标 `false`。

这里有个容易搞错的地方：**默认值会随 `output` 翻转**。`output: 'static'` 下默认预渲染，
`output: 'server'` 下默认按请求渲染。不写 `prerender` 的页面，在 SSR 模式下每次访问都会执行一遍，
而且不报错，只是慢——属于不容易发现的那类问题。

构建产物也因此分成两份，都得进镜像：`dist/client` 是静态资源和预渲染的 HTML，
`dist/server/entry.mjs` 是服务入口。只拷前者，容器能启动，但每个请求都 500。

## 几个真正花时间的坑

**适配器的大版本要和框架对齐。** 主题锁的是 `astro@6.4.8`，我装 `@astrojs/node` 时没指定版本，
拿到 11.x，它的 peer 是 `astro ^7.2.1`。结果是：构建全绿、产物齐全，直到启动才报
`app.getLogger is not a function`。能构建 ≠ 能启动，装适配器前先看 `peerDependencies`。

**正文里的远程图片会让构建依赖外部站点。** Astro 要在构建期下载图片推算宽高，
图片来源的 CDN 抖一下，构建就失败——而那段代码把真实异常吞成了一句
`Failed to parse image reference`，看着像语法错误，实际是网络问题。图片放本地就没这回事。

**nginx 启动时会解析所有 upstream。** 删掉一个服务但忘了删它那段 `location`，
nginx 直接 `host not found in upstream` 退出，然后被重启策略拉起来反复重试。
加 `location` 等于给 nginx 增加一条启动硬依赖，删服务时要成对删。

**`env_file` 指向不存在的文件会让整份编排解析失败。** 它不像 `environment` 有默认值兜底，
少一个 `.env` 文件，`docker compose ps` 都跑不了。

**`nginx -s reload` 不会重新读挂载。** 改 `conf.d` 里的内容可以热加载，
但改 `volumes` 必须重建容器。这两件事经常被当成一件。

## 资源账

跑起来之后实测：

| 项 | 数值 |
|---|---|
| site 常驻内存 | 约 62 MiB（限制 256m） |
| 构建产物 | client 8.3 MB + server 1.9 MB |
| 镜像大小 | 849 MB（node:22-slim 加生产依赖） |
| 构建耗时 | 约 26 秒（bun 装依赖） |

真正紧张的不是运行时，是构建。Astro 加图片处理和搜索索引，峰值能到 1.5G 以上，
而构建不受容器内存限制管束——它是一次性的 `docker build`。在 2G 的机器上构建前，
最好先把数据库停了腾地方，否则构建和数据库抢内存，内核挑一个杀掉，通常是数据库。

## 结语

这套东西没什么新鲜的：容器、反代、分层，都是标准做法。真正花时间的部分，
是那些"看起来应该能跑、结果没跑"的细节——版本对不上、网络依赖、启动顺序。

写下来主要是因为下次还会忘。
